# Безопасность демо

Приложение предназначено для локальной демонстрации на синтетических данных.
Для входа не нужны ФИО, телефон, email, табельный номер, билеты или медицинские
данные. Пять персон в `backend/app/application/demo_personas.py` — вымышленные
учебные профили; сценарии также синтетические. API входа принимает только ID из
этого списка и отвергает дополнительные поля. Не вводите реальные ПДн в контент.

## Граница доверия

- Клиент отправляет ID сценария, узла, выбора, команды и ожидаемую ревизию.
  Баллы, эффекты, переход, время, владелец и XP не принимаются от клиента.
  Начальные loyalty/safety — 50/50; баланс, clamp и награды вычисляет сервер.
- Движок независим от HTTP, проверяет текущий узел, доступность выбора и порядок
  решений. Декларативные условия не исполняют произвольный код. JSON-снимки
  восстанавливаются повторным исполнением журнала по закреплённой версии сценария.
- Невозможные переходы возвращают 409; неизвестные поля и неправильные типы —
  422. Отклонённая команда не меняет состояние. Исключение: уже наступивший
  **серверный** timeout сохраняется даже при отклонении опоздавшего решения.
- PostgreSQL `FOR UPDATE` сериализует решение и timeout. Время берётся из БД
  после получения блокировки. Worker не зависит от открытого браузера.
- Ключ старта уникален в пределах пользователя; ID решения привязан к исходной
  команде. Повтор не создаёт новые эффекты. Награда уникальна по session_id,
  начисление и финальный переход проходят в одной транзакции. Открытие достижения
  уникально по пользователю и версии достижения.
- Лидерборды и прогресс доступны только для чтения и строятся из результатов.
  Даже контрактный POST HR/LMS ничего не записывает и возвращает 501.
- Доступ к сессиям, результатам, debrief и уведомлениям проверяется по bearer
  identity. Несуществующая и чужая сессия дают одинаковый 404. Отметка read/unread
  принадлежит только владельцу уведомления.

## Ограничения хранения и HTTP

Миграция `20260926_06` проверяет соответствие JSON-снимка ID, версии, состоянию
и ревизии строки; обязательные поля и типы; XP в пределах 0–130 для rule_version 1;
числовые неотрицательные целые очки компетенций; boolean-журнал critical;
формат SHA-256 хеша demo-токена и валидность ключа старта. Эти CHECK-ограничения
дополняют проверку журнала движком, а не дублируют правила переходов в SQL.
Миграция не исправляет и не удаляет несовместимые данные молча: при нарушении
нужно исследовать запись до применения ограничения.

API ограничивает тело запроса 64 KiB, включая поток без Content-Length.
Идентификаторы команд ограничены 128 символами без управляющих символов,
ревизия — диапазоном PostgreSQL integer. Размеры сценариев ограничены отдельным
импортёром. API возвращает единый JSON ошибки; неожиданные исключения и ошибки
БД не раскрывают пользователю traceback, SQL, пути или параметры соединения.
Ответы API имеют `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`.

Токен demo-входа случайный, действует 24 часа; БД хранит только SHA-256 хеш.
Браузер хранит токен и намерение команды в sessionStorage, а не авторитетные
баллы. React выводит текст сценария без HTML-интерпретации; изменённые локальные
намерения проходят повторную валидацию и не могут содержать дополнительные эффекты.

## Секреты и запуск

`.env` и `.env.*` исключены из Git и Docker context; в репозитории есть только
`.env.example` с пустым паролем и явным placeholder URL. Пароль задаётся локально.
Не отправляйте содержимое `.env`, bearer-токены или дампы БД в issues и логи.
При случайной публикации секрета сначала отзовите/замените его; удаление файла
из нового коммита само по себе не удаляет значение из истории.

Compose публикует порты только на loopback. `DEMO_AUTH_ENABLED` по умолчанию
выключен в приложении; пример окружения включает его для локальной демонстрации.
**Demo-вход не подтверждает личность:** любой участник демо может выбрать любую
учебную персону. Это не разграничение реальных работников и не production-auth.
Для рабочего развёртывания отдельно нужны настоящая аутентификация/роли, TLS,
rate limiting, защита от медленных соединений, аудит доступа, резервные копии,
политика хранения/удаления и регулярная проверка зависимостей. Текущий этап их
не реализует. Прямой доступ администратора к БД находится вне модели клиентского
антифрода; SQL-ограничения не являются защитой от владельца БД.

## Проверка

Из `backend/`: `python -m pytest`, `python -m ruff check .`, `python -m mypy app`.
Для тестов транзакций/конкуренции обязателен `TEST_DATABASE_URL` с отдельной
тестовой PostgreSQL и правом создавать временные схемы. Без переменной эти тесты
пропускаются; такой запуск не подтверждает безопасность транзакций.
Из `frontend/`: `npm test`, `npm run lint`, `npm run typecheck`,
`npm run typecheck:e2e`, `npm run test:e2e`. E2E требует запущенный backend,
миграции, импорт synthetic-сценариев и включённый demo-вход.

Набор проверяет подделку баллов/эффектов/владельца/времени, невозможные переходы,
восстановление после отклонения, конкурентные повторы терминального решения,
гонки HTTP/worker, откат при ошибке записи, изоляцию пользователей, скрытие
внутренних ошибок, ограничения БД, локальную подмену состояния и отображение
недоверенного текста. Playwright проходит выбор → два решения → итог → debrief.

На этапе 11 просмотрены отслеживаемые файлы и доступная Git-история: `.env`
не отслеживается; известные форматы токенов/ключей и значения локальных секретов
в проверенных объектах не обнаружены. Это проверка заданных шаблонов, не гарантия
отсутствия любых возможных секретов и не внешний аудит безопасности.
