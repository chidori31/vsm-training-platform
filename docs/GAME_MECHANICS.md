# Игровые механики: этап 5

Сервер ведёт два независимых показателя, сохраняет объяснение каждого изменения
и автоматически применяет исход просроченного решения. Игрового экрана пока нет:
механики доступны через минимальный HTTP API и проверяются отдельно от браузера.
Сценарии остаются синтетическими примерами, их числа не являются утверждённой
балансировкой учебного продукта.

## Два показателя и журнал

| Показатель | Старт в API | Границы в API | Назначение |
| --- | --- | --- | --- |
| `passenger_loyalty` | 50 | 0–100 | Последствия выбора для лояльности пассажира |
| `safety_rating` | 50 | 0–100 | Последствия выбора для безопасности |
| `competency` с `competency_id` | 0 | Не ограничены | Баллы объявленной компетенции внутри попытки |

Loyalty и Safety не вычисляются друг из друга и не сводятся в общий балл.
Выбор может повышать один показатель и снижать другой. Если его эффекты
затрагивают только Loyalty, Safety остаётся прежним.

Для каждой затронутой метрики движок сначала суммирует все дельты решения,
затем один раз применяет границы:

```text
requested_delta = сумма дельт этой метрики
after = min(maximum, max(minimum, before + requested_delta))
applied_delta = after - before
```

Например, при Loyalty 95 эффекты `+10` и `-5` дают сумму `+5`, итог 100
и фактическое изменение `+5`. При Loyalty 98 и эффекте `+10` итог также 100,
но фактическое изменение равно `+2`. При Safety 3 и эффекте `-8` итог равен 0,
а фактическое изменение — `-3`. Компетенции получают сумму без clamp.

В `Decision.score_changes` сохраняется одна запись на затронутую метрику:

```json
{
  "metric": "passenger_loyalty",
  "competency_id": null,
  "before": 98,
  "requested_delta": 10,
  "after": 100,
  "applied_delta": 2,
  "explanation": "В синтетической модели этот выбор повышает доверие."
}
```

`applied_delta` вычисляется как `after - before`, явно включается в JSON
и проверяется при загрузке. Журнал содержит и попытку увеличить 100 на 10, даже если итог
остался 100. Сумма дельт 0 также сохраняется, если метрика была затронута.
Незатронутые показатели не получают записей. Порядок журнала соответствует
первому появлению каждой метрики в эффектах. Объяснение берётся из выбранной
версии сценария, исходные эффекты тоже сохраняются в решении.

`ScoreBounds` и `ScoringPolicy` — неизменяемые доменные значения. Границы Loyalty
и Safety задаются независимо, minimum не может превышать maximum. Чистый
`start_session` принимает явные начальные баллы и необязательную политику;
стартовые Loyalty/Safety должны входить в её диапазоны. Политика закрепляется
на всю попытку. HTTP API использует 50/50, компетенции 0 и диапазоны 0–100;
изменять их из запроса нельзя. Между попытками баллы пока не переносятся.

## Серверный таймер

Deadline — время входа в текущий узел плюс его `time_limit_seconds`.
Входом считается `started_at` либо время последнего принятого решения.
Обычный выбор разрешён при `server_time < deadline`; при равенстве и позже
приоритет имеет отдельная timeout-ветка сценария. Terminal не имеет таймера.

`SessionService` сначала получает блокировку строки `SELECT FOR UPDATE`,
затем отдельным запросом читает PostgreSQL `clock_timestamp()`. Это реальное
время после ожидания блокировки. Время начала HTTP-запроса, время транзакции
и часы браузера не решают, успел ли игрок.

Worker `python -m app.worker` опрашивает сохранённые deadline независимо от
HTTP-запросов. Он использует `FOR UPDATE SKIP LOCKED`, поэтому несколько
экземпляров не обрабатывают одну строку одновременно. Каждая попытка обновляется
в отдельной транзакции. При гонке worker и выбора блокировка сериализует
действия; проигравшая команда видит уже сохранённое состояние.

GET сессии и POST решения также проверяют просроченный deadline. Если новый
выбор опоздал, сервер сначала сохраняет timeout, а затем возвращает 409.
Отмена запоздалого выбора не откатывает автоматический переход. Клиентский
`decision_id` не может начинаться с `timeout:`: этот префикс принадлежит серверу.

Один вызов обработки срока выполняет один переход. Если timeout ведёт в новый
узел с таймером, новый deadline считается от фактического времени обработки,
а не от старого deadline. При паузе worker цепочка узлов не проигрывается
задним числом. Сроки и история хранятся в PostgreSQL: после рестарта worker
продолжает поиск просроченных попыток, без восстановления таймеров из памяти.

`TIMER_POLL_SECONDS` — положительное конечное число секунд, по умолчанию `1`.
Автоматический переход может быть сохранён с задержкой опроса, обработки очереди
или недоступности БД; точность до миллисекунды не гарантируется. GET/POST
согласуют срок при своём обращении. После ошибки БД worker повторяет опрос;
повреждённая сессия записывается в лог и пропускается в текущем проходе.

## Сохранение, повторы и восстановление

Миграция `20260926_02` создаёт `scenario_sessions` с FK на версию сценария.
JSONB `snapshot` содержит состояние, начальные баллы, политику, историю решений
и журнал. Отдельно хранятся revision, state и индексируемый deadline.
Revision равен числу принятых решений; `expected_sequence` команды сравнивается
с этим числом в заблокированном состоянии.

Решение, баллы, журнал и новый deadline сохраняются атомарно. Две одинаковые
отправки одного принятого `decision_id` дают `accepted` и `duplicate`, с одним
начислением. Повтор должен содержать те же node_id, choice_id и expected_sequence.
Другие параметры с тем же ID отклоняются. Два разных ID с одним ожидаемым
номером не могут оба примениться: после первого второй получает конфликт.

Идентичный повтор подтверждает исходный `acknowledged_decision_id` и возвращает
актуальное состояние сессии. В нём уже могут быть последующие решения или
таймаут следующего узла; повтор не возвращает старый снимок и не начисляет баллы.

JSON-снимки имеют `format_version: 2`. При сохранении и чтении движок заново
исполняет историю и проверяет путь, таймеры, политику, эффекты и журнал.
Формат 1 явно отклоняется: в нём отсутствуют закреплённые границы и журнал;
автоматическая миграция могла бы выдумать прежнюю политику. До этапа 5 таблицы
сессий не было, поэтому новая миграция не преобразует ранее сохранённые
внешние JSON-файлы. JSON-формат сценария по-прежнему имеет `schema_version: 1`.

## HTTP API после этапа 6

Актуальный контракт — [API.md](API.md). Маршруты находятся под `/api/v1`.
Demo-вход выдаёт bearer-токен; владелец сессии берётся из него. POST `/sessions`
требует Idempotency-Key и scenario_id/scenario_version, без employee_id.
Повтор старта возвращает ту же попытку и не перезапускает таймер.

GET сессии возвращает снимок v2, серверное время, deadline, текущий узел,
доступные варианты и expected_sequence. POST решения принимает decision_id,
node_id, choice_id и expected_sequence. Конфликты используют общий error/data:
при позднем выборе timeout уже сохранён, актуальное состояние находится в data.
GET `/sessions/{id}/result` доступен после завершения; история решений
поддерживает пагинацию. Все операции с сессией проверяют владельца.

Прежние неверсионированные `/sessions` удалены. Правила баллов, границ,
таймера, детерминизма и атомарного сохранения, описанные выше, сохранены.

## Запуск и проверки

Полный порядок Compose и локальная настройка — в [README.md](../README.md).
Сначала поднимите БД/backend и примените `alembic upgrade head`, затем запустите
все сервисы. Compose содержит `timer-worker` с `restart: unless-stopped`;
импорт демо остаётся отдельным явным действием. Логи worker:

```sh
docker compose logs -f timer-worker
```

Unit-тесты проверяют независимость показателей, границы, сумму до clamp, журнал,
повторы и восстановление. PostgreSQL-тесты проверяют атомарность, двойную отправку,
конкуренцию с worker, серверное время после блокировки и обработку сохранённых
сроков. Для них нужен `TEST_DATABASE_URL`; они работают в отдельных тестовых
схемах. HTTP-тесты проверяют форму команд, ответы и запрет управления временем
и баллами из клиента. Команды проверки приведены в корневом README.
