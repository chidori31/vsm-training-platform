# Игровая смена: интерфейс проводника

## Границы этапа 7 (история)

Один законченный путь: выбор ситуации → разговор и действия → разбор сохранённой
попытки. Профиль, лидерборд, награды и редактор сценариев на этом этапе не создаются.
Движок, правила, PostgreSQL и REST-контракт этапов 4–6 не меняются.
Этап 8 расширяет этот интерфейс паспортом, наградой и рейтингом; актуальные
правила и границы описаны в [GAMIFICATION.md](GAMIFICATION.md).

Порядок реализации: согласовать отображение существующего API, проверить клиент
и повторы запросов, собрать рабочую сцену, проверить мобильный/клавиатурный путь
и реальные серверные таймауты, затем commit и push текущей ветки.

## Визуальные решения

- Тёмная служебная полоса, светлый рабочий холст и железнодорожная типографика
  Bahnschrift с системными fallback. Шрифты и картинки не загружаются извне.
- Главный объект — реплика и персонаж у окна вагона. Иллюстрация — локальный SVG;
  выбор ситуации оформлен строками табло, действия — крупными кнопками.
- Контрастная жёлтая область времени и независимые шкалы доверия/безопасности.
  Изменения показывают именно применённую сервером дельту, включая clamp.
- Линия маршрута отражает посещённые сцены, а не выдуманный процент прохождения
  нелинейного графа. При циклах посещения остаются отдельными точками.
- Переход сцены занимает 280 мс и не блокирует ввод. Движение за окном деликатное;
  `prefers-reduced-motion` полностью отключает анимации и переходы.

## Разделение ответственности

`frontend/src/App.tsx` отображает каталог, текущую сцену, действия, журнал,
показатели и сетевые состояния. `runner/PassengerPortrait.tsx` и `sceneContent.ts`
содержат только визуальное представление. Реплики трёх демо синтетические.
Оригинальный текст узла доступен в «Контекст ситуации». Представление закреплено
за ID и версией 1; неизвестные сценарии/узлы и новые версии показывают исходный
текст. Варианты, условия, сроки, последствия и баллы всегда приходят из API.
Добавление новой ветки в JSON не требует менять интерфейс.

`runner/api.ts` — HTTP, ограничение времени запроса, проверка ответов и перевод
ошибок в понятный текст. `runner/useScenarioRunner.ts` управляет жизненным циклом
запросов, demo-входом, сохранением команды, повтором и опросом состояния. Обработчик
React не исполняет условия или эффекты движка и не вычисляет итоговые очки.

## Время, решения и восстановление

1. При открытии выполняется demo-вход, затем загружается каталог. Токен с TTL
   сохраняется только в `sessionStorage`. Demo-вход должен быть включён на backend;
   выбранная учебная персона синтетическая и не удостоверяет личность сотрудника.
2. Только кнопка старта создаёт попытку. До POST сохраняются случайный
   `Idempotency-Key`, ID и версия сценария. Неизвестный результат запроса повторяется
   с тем же ключом, в том числе после перезагрузки вкладки.
3. Перед отправкой выбора сохраняются `decision_id`, `node_id`, `choice_id` и
   `expected_sequence`. Пока исход неизвестен, другие действия блокируются.
   Восстановление связи повторяет ту же команду, не создавая новый выбор.
4. Успешный ответ заменяет весь отображаемый снимок. При конфликте 409 принимается
   актуальное `data` из ошибки. Никаких оптимистических переходов или начислений нет.
5. Отсчёт опирается на `server_time`, `deadline` и монотонный `performance.now()`.
   При нуле ввод закрывается, но переход происходит только после серверного ответа.
   Во время критического узла состояние опрашивается каждые 3 секунды, также при
   достижении нуля и возвращении во вкладку. Реальный timeout сохраняет backend/worker.
6. Потеря сети показывает предупреждение и кнопку «Восстановить связь». Событие
   `online` также запускает восстановление. При 401 токен обновляется один раз,
   исходная команда и выбранная персона сохраняются. Запрос ограничен 8 секундами.
7. После завершения показываются серверный результат и журнал с объяснениями.
   «Выбрать другую ситуацию» снимает привязку вкладки; запись в БД остаётся.

Фоновые чтения отменяются при выборе; устаревший ответ не должен перезаписать
новый узел. React StrictMode и размонтирование отменяют запросы и обработчики.
Локальное хранилище не является источником баллов или условий. Если сохранение
команды в браузере недоступно, POST не отправляется и показывается ошибка.
Новые действия без сети не принимаются: здесь нет очереди произвольной offline-игры.

## Доступность и адаптивность

Нативные radio и button работают через Tab, стрелки, Space и Enter. Есть ссылка
пропуска к основной сцене, видимый фокус, фокус заголовка при переходе, подписи
показателей и `aria-current` для маршрута. Ошибки объявляются как alert, принятие
решения — status; секундный отсчёт не создаёт ежесекундных live-объявлений.
Иллюстрация декоративная, роль персонажа дублируется текстом.

На телефоне иллюстрация становится узкой сценой, приборы и варианты занимают
всю ширину; длинные реплики переносятся. На этапе 8 вне активной попытки доступны
«Мой прогресс» и «Рейтинг»; навигация не отвлекает от текущего решения.

## Запуск и проверка

Сначала запустите backend/PostgreSQL/worker, примените миграции и импортируйте
три демо по [README](../README.md). В backend включите `DEMO_AUTH_ENABLED=true`.
После `npm ci` из `frontend/`:

```sh
npm run dev
npm test
npm run lint
npm run typecheck
npm run typecheck:e2e
npm run format:check
npm run build
npx playwright install chromium
npm run test:e2e
```

Playwright сам поднимает Vite на `127.0.0.1:5175`, backend должен быть доступен
на `127.0.0.1:8000` (либо через `API_PROXY_TARGET`). При наличии установленного
Edge можно задать `PLAYWRIGHT_CHANNEL=msedge` (`$env:PLAYWRIGHT_CHANNEL='msedge'`
в PowerShell). E2E используют реальную локальную БД и создают только синтетические
demo-попытки; рабочие записи не очищаются. Повторные запуски добавляют новые попытки.

Vitest проверяет контракты, состояния экрана, server-clock countdown, конфликт,
приоритет команды над опросом, двойной клик, потерянное подтверждение, перезагрузку
и недоступное хранилище. Playwright проверяет полное прохождение, реальный
20-секундный таймаут, потерю ответа после сохранения, повтор и перезагрузку,
клавиатуру, мобильную ширину и reduced motion. Скриншоты и traces сохраняются
в игнорируемом `frontend/test-results/`; их нельзя публиковать с реальными токенами.

## Ограничения

Попытка привязана к одной вкладке через sessionStorage; синхронизация нескольких
вкладок и выбор старых попыток — будущая работа. История выбранной demo-персоны
общая для использующих её участников. Балансировка,
профессиональная валидация учебных материалов и production-аутентификация требуют
отдельного этапа. Медицинский демо проверяет коммуникацию движка, не обучает лечению.
