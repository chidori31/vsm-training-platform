# Рабочая смена в реальном времени

## Запуск и режимы

На главной — «Смена». Один запуск длится 1200 секунд серверного времени.
Схема вагона показывает шесть зон, местонахождение проводника, пассажиров и
поступившие обращения. Щелчок по зоне открывает контекст; для взаимодействия
нужно выполнить предложенное действие перехода. «Тренировки» и `/#training`
содержат прежние графовые сценарии и короткую последовательную смену.

Сначала доступны сообщение пассажира и наблюдения. Осмотр открывает факты,
проверка уточняет обстоятельства. Внутренние состояния NPC и будущая очередь
последствий не возвращаются браузеру. Вероятные причины нельзя считать фактами.

## Время, состояния и последствия

Поезд движется по условному маршруту Москва → Тверь → Великий Новгород →
Санкт-Петербург. Станции содержат arrival/departure, стоянки разрешают отдельные
служебные действия. До станции можно подготовить документы, а передать их —
только в пределах стоянки. Игрок не управляет часами или движением поезда.

Чистые функции `start`, `advance`, `act` работают с immutable dataclasses.
`advance` обрабатывает все наступившие Consequence по `(at_seconds, id)`, с
запланированными временными отметками. Временное событие имеет приоритет перед
командой на той же секунде. Скачок после простоя даёт тот же результат, что polling.

Incident: reported → investigated → confirmed → handled → resolved.
Пропуск времени может дать ignored → escalated → critical. Успешное действие
может ожидать проверки результата; нет обязательного единственного порядка
обслуживания обращений. Отсрочка не останавливает эскалацию. Ограничение опасной
зоны отменяет дальнейшие соответствующие ухудшения.

NPC сохраняет mood/stress/health/satisfaction/trust/currentNeeds/history. Просьба
и позднее сообщение о самочувствии связаны с одним пассажиром: прежнее общение
влияет на последующее уточнение. Все персонажи и параметры синтетические.

Оборудование находится в определённых зонах; его необходимо взять перед
применением. Запрос службы сохраняет время отправки/ожидаемого ответа и результат.
Ожидание одного ответа пересекается с новыми обращениями. Завершение одной задачи
не останавливает остальные. Лечение, реальная медицинская диагностика и внешняя
диспетчерская интеграция не моделируются.

## Хранение, безопасность и восстановление

PostgreSQL хранит pinned JSON definition/hash, seed и snapshot; отдельные таблицы —
receipts команд и неизменяемые rewards. Snapshot принимается только при совпадении
с повторным выполнением серверного журнала. Worker и HTTP используют один сервис.

Операция: lock owned row → DB clock → catch-up → receipt → revision → действие →
atomic snapshot/receipt/audit. При неверной новой команде catch-up сохраняется,
возвращается409, интерфейс обновляет состояние без автоматического повторного выбора.
Одинаковый command_id+payload возвращает текущую проекцию даже после завершения.
Повтор идентификатора с другим payload отклоняется. Клиент не передаёт seed,
время, баллы, факты или стадии. `.env` содержит только локальную конфигурацию.

Получение `/current` может продвинуть время и сохранить последствия. После закрытия
страницы работает timer-worker; после остановки всех процессов следующий запуск
догоняет время. На1200секундах результат замораживается. При откате часов elapsed
не уменьшается. Физическая пауза и пользовательская перемотка отсутствуют.

## Результат и награда

Safety, Service, Regulation, Prioritization, Communication — шкалы0–100.
ReactionTime — среднее задержек между сообщением и первым содержательным действием.
Временные поля debrief `*_at_seconds` и `first_reaction_seconds` — абсолютные T+
от начала смены; UI дополнительно показывает задержку относительно сообщения.

В завершённой смене с содержательным действием по инциденту:
`XP = min(130, 20 + 15 × resolved + floor(sum(пяти шкал) / 25))`.
Без таких действий XP=0; перемещение, взятие оборудования и отсрочка не дают XP.
Награда записывается один раз через DomainEvent и reducer RewardTransaction.
Нулевая награда сохраняет receipt, но не создаёт фиктивное EARN.

Профиль и leaderboard суммируют XP отдельных тренировок и операционных смен.
`completed_sessions` в существующем DTO означает завершённые учебные единицы
обоих режимов. Новые учебные достижения сохраняются с результатом и видны в
профиле; это не реальные профессиональные допуски. Положительные фактические изменения регламента и коммуникации сохраняются в
completion-event и добавляются к очкам компетенций профиля. Это накопленные
учебные очки; итоговые профессиональные шкалы смены остаются отдельными.
Session-specific челленджи и
подробная графовая аналитика сохраняют собственную область применения.

«Чёрный ящик» показывает структурированные события с изменениями метрик,
первым осмотром/реакцией/завершением. Фильтр выделяет одно обращение. Альтернативы
написаны автором контента и не претендуют на точную симуляцию другой вселенной.

## Контент и изменение сценария

Файл: `scenarios/simulation/demo-v1.json`. Строгая Pydantic-схема:
`backend/app/simulation/schema.py`. Конкретные глаголы и правила:
`backend/app/domain/simulation.py`; это предметный слой, не универсальный DSL.
В JSON редактируются сообщения, наблюдения, причины, альтернативы, допустимые зоны,
время поступления, служба/оборудование/станция. Неизвестные поля, дубли ID и
невалидные ссылки/расписания отклоняются; JSON ограничен128KiB.

Для новой публикации увеличьте version и создайте новый файл; настройте
`SIMULATION_DEFINITION` на backend, если используете иной путь. Уже начатые смены
используют закреплённый документ. После публикации изменение семантики движка
требует поддержки старой версии или явной миграции, а не молчаливого изменения v1.

## Проверки

Домен проверяет catch-up, вариативность seed, ветви, скрытые данные, оборудование,
параллельность, связь, NPC, station windows, шкалы и воспроизводимость.
PostgreSQL/API-тесты используют отдельные схемы: ownership, rowlock/clock, receipts,
отказ команды, catch-up, settlement, audit, восстановление, tampering, rate limit.

Полный браузерный тест использует явную тестовую инъекцию часов через Python-сервис
в локальном Docker-контейнере. Публичного endpoint перемотки нет. Для повторения
из `frontend/` на синтетической БД работающего Compose (PowerShell):

```powershell
$env:PLAYWRIGHT_BASE_URL='http://127.0.0.1:8080'
$env:PLAYWRIGHT_CHANNEL='msedge'
$env:PLAYWRIGHT_SIMULATION_CONTAINER='vsm-training-backend-1'
npm run test:e2e -- e2e/simulation.spec.ts
```

Тест продолжит/завершит незаконченный **синтетический** рейс `demo-employee`,
создаст новый, выполнит действия через UI, проверит параллельные события и полный
debrief. Тестовый helper не переписывает snapshot или баллы. Без явного container
этот специальный E2E пропускается; unit/API-тестам Docker-clock опция не нужна.
