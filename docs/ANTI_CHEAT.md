# Anti-cheat учебного тренажёра

Этот слой относится к тренировкам проводника. Он не вводит пассажирскую валюту,
денежные призы, проверку личности или автоматические баны. Баллы и сроки определяет
сервер; сигнал аномалии требует проверки и сам по себе ничего не доказывает.

## Что уже было закрыто

До этого этапа клиент уже не мог назначить XP, safety, loyalty, эффекты, владельца
или серверное время: строгие DTO отвергают лишние поля. Движок проверяет текущий
узел, доступность выбора, закреплённую версию и expected_sequence. История
восстанавливается повторным исполнением, поэтому пропуск шага и подмена порядка
отклоняются. Отдельного клиентского «завершить успешно» нет.

PostgreSQL блокирует строку попытки до чтения серверного времени. Решение на
границе deadline проигрывает timeout; закрытие вкладки и подмена Date.now() не
останавливают worker. При позднем запросе timeout сохраняется и при ответе 409.
Идентичная команда повторно возвращает актуальную сессию. Другое содержимое под
тем же ID конфликтует. Награда уникальна по session_id и сохраняется вместе с
финальным переходом; клиентское хранилище содержит лишь намерение повторить команду.

Две вкладки, браузера или устройства могут открыть одну попытку. Это разрешено:
первая допустимая команда меняет ревизию, устаревшая команда отклоняется, точный
повтор не даёт вторую награду. Это сериализация действий, а не запрет второго
устройства. Для отдельной новой попытки действуют самостоятельные правила награды.

## Какие пробелы закрывает этот этап

Раньше не было общего долговечного лимита частоты команд и журнала отклонённых
попыток/повторов. Можно было создавать много новых попыток и запросов, не оставляя
отдельных признаков автоматизации. Серверная однократность одной награды при этом
уже существовала; мы не выдаём её за вновь исправленную уязвимость.

Миграция `20260926_08` добавляет `rate_buckets` и `command_audits`, после
`20260926_07`. Миграции обратимы; downgrade удаляет только эти новые таблицы и
функцию защиты журнала. Обычные команды приложения не удаляют историю аудита.

### Общие лимиты PostgreSQL

| Команда              | Ключ лимита          | По умолчанию за 60 секунд | Переменная окружения                  |
| -------------------- | -------------------- | ------------------------- | ------------------------------------- |
| Demo login           | Один общий для демо  | 120                       | `RATE_LIMIT_AUTH_PER_MINUTE`          |
| Старт сценария       | Серверный ID персоны | 60                        | `RATE_LIMIT_START_PER_MINUTE`         |
| Решение сценария     | Серверный ID персоны | 240                       | `RATE_LIMIT_DECISION_PER_MINUTE`      |
| Старт смены          | Серверный ID персоны | 30                        | `RATE_LIMIT_SHIFT_START_PER_MINUTE`   |
| Следующий этап смены | Серверный ID персоны | 120                       | `RATE_LIMIT_SHIFT_ADVANCE_PER_MINUTE` |

Окно начинается с первой разрешённой команды и не продлевается отказами. Счётчик
блокируется через FOR UPDATE; время БД читается после блокировки. Новый процесс,
несколько workers и перезапуск API не сбрасывают окно. Поддерживаются положительные
лимиты до 100000; ошибочная конфигурация не отключает защиту молча.

Превышение возвращает 429 `rate_limited` и `Retry-After` в секундах. Сам счётчик
фиксируется независимо от результата игровой команды: отклонённые и повторные
запросы также расходуют квоту. Проверка авторизованных команд выполняется после
установления персоны и до обработки DTO/перехода. Auth лимит применяется перед
проверкой DTO и выдачей токена; неверное значение персоны также расходует квоту
и оставляет обезличенный отказ. Синтаксически неверный JSON не доходит до этой
проверки и не создаёт токен. Лимиты не зависят от IP, User-Agent, устройства или
клиентского таймера.

### Долговечный аудит

Принятый переход, повтор, конфликт и отказ по сохранённой сессии записываются
в транзакции сессии. Ошибка записи откатывает переход и награду. Timeout worker
оставляет отдельное событие с actor `system:timer`. Если HTTP-команда одновременно
провоцирует timeout, журнал различает серверный переход и ответ на команду игрока.

Строка содержит серверный UUID события, тип, fingerprint, actor, попытку и версию
сценария, серверное время, client command ID, прежний/новый статус и ревизию,
expected_revision, node/choice, результат XP и список флагов. `xp_total` — текущая
награда попытки, `xp_granted` — начисление именно этим переходом; replay имеет 0.
Общий DomainEvent используется для валидации и fingerprint серверного события,
без подключения пассажирского EARN-прототипа к учебному XP.

Авторизованные HTTP-отказы до получения доверенного снимка пишутся отдельно с
кодом ошибки и без чужого состояния, сырых тел, токенов и сетевых идентификаторов.
Поэтому у schema/ownership-отказа поля attempt/client ID могут быть пустыми.
При недоступной БД такой отказ сохраняет исходный безопасный HTTP-ответ; потеря
его аудита отмечается в серверном логе. Это исключение не касается принятых
переходов: для них транзакционная запись обязательна. Выдача demo-токена и её
аудит — отдельные транзакции; ошибка аудита не выдаёт токен в ответе клиенту.

Триггер PostgreSQL запрещает UPDATE/DELETE строки `command_audits`. Fingerprint
помогает идентифицировать содержание, но не является цифровой подписью.
Владелец БД может отключить триггер: это не защита от администратора.

### Флаги для проверки

| Флаг                        | Наблюдение                                                                                                           |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `fast_decision`             | Принятое решение менее чем через 0,4 секунды после входа в узел                                                      |
| `rapid_completion`          | Завершение с решением менее чем за 1 секунду от старта                                                               |
| `frequent_replay`           | Не менее пяти повторов персоны за последние 60 секунд                                                                |
| `conflicting_command`       | Повтор ID с конфликтом или устаревшая ожидаемая ревизия                                                              |
| `many_parallel_sessions`    | При старте сохранено не менее пяти активных попыток персоны                                                          |
| `repeated_perfect_sequence` | Не менее трёх одинаковых завершённых маршрутов одной версии без timeout/снижения метрик, с safety/loyalty не ниже 50 |

Это прозрачные эвристики, не оценка способностей и не основание для наказания.
Флаги повторов и конфликтов вычисляются общим журналом для команд сценария и
смены, включая повторы уже завершённой смены; начисление XP при таком повторе равно нулю.
Время включает серверную/сетевую задержку, а не измеряет чистое время размышления.
Повторный запрос нормален после потери ответа; одинаковая хорошая ветка нормальна
при обучении. Общая demo-персона смешивает действия нескольких посетителей.
Параллельный агрегат может быть приблизительным при одновременных стартах.
Флаги не меняют XP, достижения, доступность выбора и профиль.

Нового публичного admin API нет. Оператор с разрешённым доступом к тестовой БД
может прочитать признаки, например:

```sql
SELECT created_at, actor_id, action, outcome, session_id, flags, reward
FROM command_audits
WHERE jsonb_array_length(flags) > 0
ORDER BY created_at DESC
LIMIT 100;
```

## Остаточные риски

- **Высокий для материальных наград:** demo-вход позволяет выбрать любую из
  пяти персон. Это не удостоверение человека и не защита от аккаунтов-ботов.
- **Высокий для соревнования:** граф и эффекты видны в каталоге; правильные
  последовательности можно автоматизировать. Новые попытки законно дают новый XP.
  Лимиты замедляют массовые запросы, но не устраняют farming.
- **Средний для локального демо:** общий auth лимит может временно затронуть
  других посетителей; персоны общие. Ограничение приложения не заменяет сетевую
  защиту, лимиты соединений, TLS и защиту от распределённой нагрузки.
- **Средний эксплуатационный:** аудит и rate buckets требуют работоспособной БД;
  роста истории, архивации, политики retention, сигнализации и нагрузочного SLA
  пока нет. Неаутентифицированные попытки с неверным bearer не связываются с лицом.
- **Не закрывается кодом клиента:** пользователь может изменить свой экран или
  sessionStorage, но такой экран не изменяет серверный результат.

Перед материальными призами нужны реальная идентификация/права, отдельные
правила допустимых попыток и выдачи, защита источников событий, операционные
лимиты и аудит доступа, независимая проверка безопасности и политика разбора
ложных срабатываний. Текущая реализация не обещает production antifraud.

## Проверки

`tests/test_security_signals.py` проверяет пороги и настройки.
`tests/timed_sessions/test_anti_cheat.py` использует PostgreSQL: конкурентные
лимиты, повтор после перезапуска сервиса, reset окна, HTTP429/422, отсутствие
сырых полей в аудите, UPDATE/DELETE запрет, replay/conflict, timeout, повторные
маршруты и откат принятого перехода при сбое аудита. Существующие engine/API/
race-тесты продолжают проверять порядок, серверный deadline и единственную награду.
