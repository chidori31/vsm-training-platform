# Обучающий разбор и аналитика компетенций — этап 9

## Назначение и архитектура

После завершения пользователь видит решение, последствие, отдельное объяснение
loyalty и safety, проявившиеся компетенции, доступные альтернативы и следующий
учебный шаг. Оценка воспроизводится локальными правилами v1 без runtime LLM.

Существующий снимок сессии v2 уже хранит структурированные события: decision_id,
sequence, node_id, choice_id, decided_at, effects, explanation и score_changes
с before/requested_delta/after/applied_delta. Он атомарно сохраняется с переходом
и проверяется повторным исполнением по закреплённой версии сценария. Повтор команды
не добавляет событие. Используем этот журнал, не дублируя его второй таблицей.
Новые миграции и изменение JSON-сценариев для этапа 9 не требуются.

Чистый домен строит типизированные факты разбора из пары Scenario/ScenarioSession.
Прикладной слой читает только попытки владельца; FastAPI сериализует результат.
React отображает серверные выводы в временной линии и линейном журнале навыков.
Сохраняются состояния загрузки, ошибки/повтора, клавиатура, мобильная версия и
prefers-reduced-motion. Смена персоны отменяет чтения прошлого пользователя.

## Правила разбора v1

Каждая запись включает исходную ситуацию, текст принятого выбора, время от входа
в узел, последствие и текст следующего узла. Обе шкалы показываются всегда:
before/after и фактическая delta; отсутствие эффекта явно означает отсутствие
изменения. При clamp отдельно объясняется отличие запрошенной и применённой дельты.
Компетенции отражают фактические изменения решения, включая отрицательные.
Временной интервал включает задержку серверной обработки timeout, поэтому не
объявляется временем размышления сотрудника. Общий авторский текст последствия
дополняется объяснением численной дельты каждой шкалы; отсутствующая в контенте
причина не придумывается.

Альтернативы оцениваются на состоянии ДО решения с той же ScoringPolicy.
Условие определяет доступность; недоступные варианты помечаются и не рекомендуются.
Служебный timeout не является альтернативой пользователя. Для timeout показываются
варианты, доступные до истечения срока, и совет уложиться в срок.
Если все пользовательские варианты были закрыты условиями, разбор прямо
объясняет отсутствие доступного действия и не советует выбрать быстрее.
Сравниваются только непосредственные эффекты: лучший будущий исход не обещается.
Альтернатива рекомендуется, если не ухудшает ни одну из шкал/компетенций и улучшает
хотя бы одну. При компромиссе нет универсально «правильного» ответа. Равные варианты
не объявляются улучшением. Наличие совета не меняет награды этапа 8.

## Аналитика v1

Баллы прогресса совпадают с этапом 8: сумма положительных итоговых приростов
компетенции завершённых попыток с действием пользователя. Net delta отдельно
сохраняет отрицательные результаты. В хронологическом ряду одна точка на завершённую
попытку, содержащую компетенцию; порядок completed_at, session_id.

Наблюдение компетенции — решение в узле, где хотя бы один доступный пользовательский
выбор имеет ненулевой эффект этой компетенции. Для timeout используется доступность
до срока; сам timeout тоже учитывается как наблюдение. Положительный/отрицательный
исход определяется фактической дельтой; нулевая дельта нейтральна.
Для вывода нужны минимум 3 наблюдения в минимум 2 завершённых попытках.
Сильная компетенция: положительных ≥70%, отрицательных ≤20%; зона развития:
отрицательных ≥30%; иначе «формируется». Без достаточных данных вывод не делается.
Это учебная эвристика, не оценка профессиональной пригодности.
Эффекты одного выбора сначала суммируются: +2 и −2 не создают наблюдение.
Practiced sessions учитывает попытки с фактической возможностью проявить навык.
Если эффект компетенции есть только у timeout, он отражается в net/trend и
паттернах, но не входит ни в числитель, ни в знаменатель оценки наблюдений.

Паттерны: timeout, safety_loss, loyalty_loss, competency_regression. Один код
считается не более одного раза на решение. Повторяющийся паттерн требует минимум
2 разных завершённых попыток; count и session_count видны пользователю.
Активные попытки входят только в статистику попыток, не в выводы о навыках.
Статистика сгруппирована по ID/версии сценария: попытки, завершения, активные,
таймауты завершённых, средняя длительность и обе конечные шкалы завершённых.
При отсутствии завершений средние null. Наборы и порядок детерминированы.
Timeout считается проблемным паттерном только при наличии доступного выбора;
неизбежные timeout при закрытых условиях остаются в фактической статистике времени.

## Контракт интерфейса

`GET /api/v1/sessions/{session_id}/debrief` — только завершённая собственная
попытка; активная 409 result_not_ready, чужая/несуществующая 404.

Ответ: rule_version=1, session_id, scenario_id, scenario_version, title,
completed_at, summary {decision_count, timeout_count, loyalty_delta, safety_delta},
decisions — упорядоченный массив:

- sequence, decision_id, node_id, node_text, choice_id, choice_text,
  destination_id, destination_text, decided_at, elapsed_seconds, was_timeout, explanation;
- loyalty и safety: {before, after, delta, requested_delta, explanation};
- competencies: [{competency_id, before, after, delta, explanation}];
- alternatives: [{choice_id, text, destination_id, explanation, available,
  loyalty_delta, safety_delta, competencies: [{competency_id, delta}]}];
- suggestion: {text, choice_ids: string[]}; pattern_codes: string[].

`GET /api/v1/analytics/me/competencies` — только данные владельца:

- rule_version=1, total_sessions, completed_sessions, active_sessions;
- decision_count, timeout_count — по завершённым попыткам;
- competencies: [{competency_id, earned_points, net_delta, positive_decisions,
  negative_decisions, opportunities, practiced_sessions,
  status: insufficient_data|strength|growth_area|developing,
  trend: [{session_id, completed_at, delta, earned_points, cumulative_points}]}];
- strengths, weaknesses — массивы competency_id;
- patterns: [{code, title, description, count, session_count, recurring, advice}];
- scenarios: [{scenario_id, scenario_version, title, attempts, completed, active,
  timeout_count, average_duration_seconds, average_loyalty, average_safety}].

Старый `/analytics/me` остаётся совместимым. Новые read models рассчитаны на
небольшое демо: limit не скрывает часть истории расчёта. Материализация и ограничение
объёма истории потребуют отдельного этапа.

## План реализации и проверки

1. Unit-тесты replay, доступности альтернатив, clamp/нулевых эффектов, timeout,
   Pareto-сравнения, порогов компетенций, паттернов и порядка истории. Реализовать
   `backend/app/domain/debrief.py` и аналитику на стандартной библиотеке Python.
2. Тесты HTTP ownership, 409, повторов и рестарта на PostgreSQL. Добавить тонкие
   routes/DTO и application service, читающий проверенные сохранённые события.
3. Vitest для временной линии, объяснений, альтернатив, недостатка данных и retry.
   Реализовать `frontend/src/learning/`, подключить разбор к завершению и аналитику
   к паспорту; сохранить прежний доступный путь прохождения.
4. Playwright с реальным backend: прохождение → разбор → альтернативы → аналитика,
   мобильная ширина, клавиатура и восстановление после ошибки. Просмотреть скриншоты.
5. Полные pytest/Vitest, lint/typecheck/format/build, Docker smoke, независимый
   review и документация. Один commit `feat: add competency analytics and debrief`,
   push текущей ветки и остановка.

Проверки особого внимания: условие альтернативы до изменения баллов; смешанные
штрафы/награды без выдуманного лучшего ответа; повтор и timeout без дублирования;
нулевые данные без ярлыка слабой компетенции; изоляция пользователей и версий.
