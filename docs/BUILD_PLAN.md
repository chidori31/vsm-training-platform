# План разработки «Геймификация для ВСМ»

## Назначение

Обучать проводников ВСМ-400 принятию решений в рабочих ситуациях через
нелинейные сценарии, ограничение времени и разбор последствий.

## Архитектура и границы

Один репозиторий: `frontend/` (React, TypeScript, Vite), `backend/` (FastAPI,
Pydantic, SQLAlchemy, Alembic), `scenarios/` (будущий контент), `infra/`
(Nginx), `docs/`. PostgreSQL — постоянное хранилище.

Frontend отвечает за отображение, ввод и состояния запросов. Backend владеет
правилами сценариев, валидацией решений, временем, очками и сохранением прогресса.
Клиент не определяет итоговые баллы и соблюдение таймера. Доступ к БД только
через backend. Контракт HTTP описан OpenAPI; в разработке Vite проксирует `/api`,
в контейнерах ту же роль выполняет Nginx. Прокси убирает префикс `/api`.

## Этап 1: технический фундамент

Порядок реализации и проверки:

1. Создать тесты HTTP-контракта и состояний экрана подключения.
2. Реализовать `backend/app/main.py`: `GET /health` → `{"status":"ok"}`;
   `GET /ready` проверяет PostgreSQL и возвращает 503 при недоступности.
   Добавить SQLAlchemy metadata и конфигурацию Alembic без доменных таблиц.
3. Реализовать `frontend/src/App.tsx`: проверка `/api/health`, состояния ожидания,
   успеха, ошибки, таймаут и повторная проверка. Проверять формат ответа.
4. Настроить Dockerfiles, Compose, Nginx и переменные окружения без секретов.
5. Выполнить форматирование, lint, typecheck, pytest, Vitest, сборку frontend,
   проверку Compose и доступные интеграционные проверки. Просмотреть diff,
   создать один bootstrap-коммит и отправить текущую ветку.

Критичные проверки: сетевой сбой, неверный JSON/контракт, HTTP-ошибка, зависший
запрос, недоступная БД. Health — признак работы процесса, не готовности БД.

## Следующие этапы (не реализованы)

2. Доменные модели и миграции: пользователь, профиль, компетенция, сценарий,
   версия сценария, узел, вариант выбора, попытка, решение, изменение баллов.
   Утвердить JSON-схему контента и правила публикации версий.
3. Движок сценариев: ветвление, диалоги, серверные сроки критических решений,
   идемпотентная запись решения, восстановление попытки после разрыва связи.
4. Игровой интерфейс: Passenger Loyalty, Safety Rating, компетенции,
   достижения, уровни и лидерборд. Сначала утвердить правила начисления баллов.
5. Разбор решений и аналитика компетенций; уведомления и настройки доставки.
6. Аутентификация и роли, защита персональных данных, API для HR/LMS,
   аудит и эксплуатация. Контракты интеграций согласовать с реальными системами.

Для этапа 3 добавить Playwright и E2E-проверки прохождения, истечения таймера,
повторной отправки решения и восстановления сессии. Пока нет соответствующих
пользовательских сценариев, Playwright не устанавливается.

## Ключевые решения

- Синхронный SQLAlchemy и psycopg: достаточно для первого этапа, без лишнего
  асинхронного слоя. Alembic управляет схемой; автоматического create_all нет.
- Pydantic фиксирует HTTP-ответы. Liveness не зависит от конфигурации БД.
- Секреты только в окружении; `.env` исключён из Git и Docker context.
- В контейнерах БД ждёт healthcheck, backend проверяет readiness, frontend
  доступен после готовности backend. Схему обновлять отдельной командой Alembic.
- Тесты: pytest для backend, Vitest и Testing Library для frontend.
- Docker Compose предназначен для локальной разработки, не production:
  аутентификация, TLS, резервное копирование и лимиты — отдельный этап.
