# План разработки «Геймификация для ВСМ»

## Текущий scope: этап 3 — формат и хранение сценариев

Новое задание владельца на этап 2 задаёт обучающую платформу ВСМ и EmployeeProfile.
Оно уточняет scope для текущей работы: проектируется исходный учебный домен.
Прежние ограничения этапа 1 сохранены ниже как история решения; пассажирская
геймификация не добавляется. Архитектура и диаграмма — в [ARCHITECTURE.md](ARCHITECTURE.md).

### Реализовано

- Этап 1: React/Vite, FastAPI health/readiness, PostgreSQL, Docker Compose,
  Alembic, конфигурация, pytest и Vitest.
- Этап 2: `backend/app/domain/` — scenario, gameplay/session, scoring,
  competencies, achievements, profiles, analytics и notifications.
- Типы EmployeeProfile, Competency, Scenario, ScenarioNode, Choice,
  ScenarioSession, Decision, Achievement, AchievementUnlock, Notification.
- Валидация графа и снимков сессии, DSL v1 условий/эффектов без eval/exec,
  неизменяемые значения, чистые расчёты и unit-тесты независимости от web/ORM.
- Этап 3: строгий JSON/Pydantic-контракт, преобразование в домен, отдельная
  timeout-ветка, объяснения последствий и настраиваемый запрет циклов.
- PostgreSQL JSONB для версий сценариев, Alembic-миграция, транзакционный импорт
  и чтение конкретной версии; повторный импорт одинакового документа безопасен.
- Три небольших синтетических демо и JSON Schema для редактора. Проверки
  валидации, CLI, round-trip хранения, конфликтов версий и миграций.

### Порядок выполнения этапа 3

1. Зафиксировать строгую схему и тесты ошибок. Внешний адаптер использует
   Pydantic, домен сохраняет зависимость только от стандартной библиотеки.
2. Добавить JSONB-таблицу, миграцию и репозиторий с транзакцией у вызывающей стороны.
   JSONB сохраняет граф целиком; отдельные таблицы узлов усложнили бы импорт
   и версионирование без пользы для текущего сценария чтения.
3. Добавить синтетический контент, команды validate/import/export-schema и
   документацию редактирования. Конфликт содержимого требует новой версии.
4. Проверить PostgreSQL в изолированных тестовых схемах, upgrade/downgrade,
   форматирование, lint, typecheck, весь pytest и существующий frontend.
5. Просмотреть diff, commit `feat: add scenario schema and persistence`, push
   текущей ветки и остановиться.

### Следующие этапы (ещё не реализованы)

4. Чистые операции start/advance и исполнение таймаутов; application use cases,

   Проверить закрепление версии, идемпотентность и конкурентные решения.

Следующий этап не начинается без отдельного задания. Этап 3 хранит сценарии;

## История этапа 1: PRODUCT SCOPE — pending clarification

Ниже сохранено прежнее решение, действовавшее до нового задания на этап 2.
Фразы о незафиксированном scope и запрете доменных типов относятся к этапу 1.

Продуктовый scope НЕ ЗАФИКСИРОВАН. Исходное официальное ТЗ описывает обучающий
симулятор для проводников, материалы QA-сессии — пассажирскую геймификацию.
Владелец репозитория должен уточнить целевую аудиторию и продуктовый scope.
До этого архитектура не закрепляет ни проводника, ни пассажира как конечного
пользователя. Следующий этап без отдельного задания не начинается.

Материалы QA-сессии обсуждают паспорт путешественника, достижения за реальные
действия и поездки, бонусную валюту «Вёрсты», челленджи, событийную модель
начисления, offline event queue, antifraud и ненавязчивую интеграцию геймификации
в основной интерфейс. Это контекст противоречия, а не утверждённые требования.

Не создаются EmployeeProfile, PassengerProfile, Scenario Engine, Miles/«Вёрсты»,
Achievements, Loyalty Program, HR/LMS integration и ticketing integration.
Доменных таблиц, миграций и бизнес-модулей на первом этапе нет.

## Исходное назначение (сохранено; не утверждённый scope)

Обучать проводников ВСМ-400 принятию решений в рабочих ситуациях через
нелинейные сценарии, ограничение времени и разбор последствий.

## Подтверждённый технический фундамент: архитектура и границы

Один репозиторий: `frontend/` (React, TypeScript, Vite), `backend/` (FastAPI,
Pydantic, SQLAlchemy, Alembic), `scenarios/` (JSON Schema и синтетические демо), `infra/`
(Nginx), `docs/`. PostgreSQL — постоянное хранилище.

Frontend отображает состояние подключения и позволяет повторить проверку.
Backend предоставляет health/readiness и проверяет соединение с PostgreSQL.
Доступ к БД только через backend. Контракт HTTP описан OpenAPI;
в разработке Vite проксирует `/api`,
в контейнерах ту же роль выполняет Nginx. Прокси убирает префикс `/api`.

## Этап 1: технический фундамент

Порядок реализации и проверки:

1. Создать тесты HTTP-контракта и состояний экрана подключения.
2. Реализовать `backend/app/main.py`: `GET /health` → `{"status":"ok"}`;
   `GET /ready` проверяет PostgreSQL и возвращает 503 при недоступности.
   Добавить SQLAlchemy metadata и конфигурацию Alembic без доменных таблиц.
3. Реализовать `frontend/src/App.tsx`: проверка `/api/health`, состояния ожидания,
   успеха, ошибки, таймаут и повторная проверка. Проверять формат ответа.
4. Настроить Dockerfiles, Compose, Nginx и переменные окружения без секретов.
5. Выполнить форматирование, lint, typecheck, pytest, Vitest, сборку frontend,
   проверку Compose и доступные интеграционные проверки. Просмотреть diff,
   создать один bootstrap-коммит и отправить текущую ветку.

Критичные проверки: сетевой сбой, неверный JSON/контракт, HTTP-ошибка, зависший
запрос, недоступная БД. Health — признак работы процесса, не готовности БД.

## Подтверждённые технические решения

- Синхронный SQLAlchemy и psycopg: достаточно для первого этапа, без лишнего
  асинхронного слоя. Alembic управляет схемой; автоматического create_all нет.
- Pydantic фиксирует HTTP-ответы. Liveness не зависит от конфигурации БД.
- Секреты только в окружении; `.env` исключён из Git и Docker context.
- В контейнерах БД ждёт healthcheck, backend проверяет readiness, frontend
  доступен после готовности backend. Схему обновлять отдельной командой Alembic.
- Тесты: pytest для backend, Vitest и Testing Library для frontend.
- Docker Compose предназначен для локальной разработки, не production:
  аутентификация, TLS, резервное копирование и лимиты — отдельный этап.
